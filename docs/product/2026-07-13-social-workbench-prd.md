# 社媒服务工作台 PRD

**版本**：v1.0  
**日期**：2026-07-13  
**产品状态**：已上线迭代版  
**产品名称**：社媒服务工作台（Social Service Workbench）

## 1. 产品概述

社媒服务工作台是面向内部客服和业务坐席的独立 IM 作业系统。坐席通过工作台查看由工作台服务账号接入的 WhatsApp（WA）和 Telegram（TG）会话，处理消息、人工回复、记录内部备注、维护工作台标签，并查看必要的发送与协作状态。

产品的核心目标是让坐席在一个连续、低干扰的作业面内完成：

```text
发现待处理会话 → 理解上下文 → 人工回复 → 记录处理状态与内部信息
```

工作台不属于监控分析产品，也不展示告警、AI 建议、供应商画像、可靠性评分、知识库或营销触达能力。

## 2. 产品边界

### 2.1 包含范围

- WA、TG 服务账号接入后的会话列表和消息线程。
- 服务账号、平台、未读、标签/分组和关键词筛选。
- 文本、附件、图片、引用回复和发送状态展示。
- 人工创建外发任务、取消、重试、已读进度。
- 会话状态、内部备注、协作查看状态、操作动态。
- 渠道原生标签/分组的只读展示和筛选。
- 工作台标签的创建、选择、取消和会话内编辑。
- 服务账号、坐席权限、发送开关、限速、熔断和审计。

### 2.2 明确不包含

- AI 生成回复、自动回复、群发、营销触达或批量私聊。
- 告警、监控分析结果、供应商画像、评分、知识库、内容模板。
- 在工作台内修改 WA 原生标签或 TG 原生文件夹。
- 工单、审批、多级流转、负责人分配、优先级和跟进提醒。
- 跨服务账号或跨平台合并客户身份。

## 3. 目标用户与权限

| 角色 | 主要目标 | 核心权限 |
| --- | --- | --- |
| 坐席 | 查看授权会话、回复客户、记录上下文 | `can_view`、`can_reply` |
| 主管/运营 | 维护会话状态、工作台标签，检查协作信息 | `can_manage` |
| 管理员 | 管理坐席、入口权限、服务账号、发送控制和范围授权 | `can_admin` |

权限以“坐席状态 + 入口权限 + 服务账号/会话范围”实时计算。坐席停用、撤销入口或收回范围后，下一次请求立即生效。

## 4. 核心使用场景

### 4.1 处理未读消息

1. 坐席进入工作台，默认查看全部或未读会话。
2. 通过平台、服务账号、标签/分组或搜索定位会话。
3. 在中栏读取消息、附件和引用上下文。
4. 在回复框输入内容并发送。
5. 工作台创建外发账本任务，渠道 Worker 串行发送并回写状态。
6. 坐席在右栏更新会话状态或添加内部备注。

### 4.2 给会话添加工作台标签

1. 坐席打开会话。
2. 在消息线程顶部右侧查看当前标签，最多直接展示 5 个。
3. 点击铅笔图标，弹出轻量标签编辑器。
4. 选择已有工作台标签，或新建并添加一个工作台标签。
5. 保存后，中栏标题和左侧会话摘要同步更新。

渠道原生标签或分组以 `WA：标签名`、`TG：文件夹名` 形式展示，只读且不会被写回渠道。

### 4.3 记录处理上下文

1. 在右栏“会话处理”选择状态：待处理、跟进中、已解决或暂停。
2. 在“内部备注”记录沟通背景、承诺事项、待办或交接信息。
3. 通过“最近动态”确认当前查看人、已读动作、标签更新和外发相关操作。

## 5. 信息架构与界面要求

### 5.1 顶部工作队列

顶部保持单行、低干扰：

- 产品名称与当前会话范围。
- 平台：WA / TG。
- 范围：未读 / 全部。
- 服务账号多选。
- 标签/分组筛选。
- 渠道分组同步入口。

不展示客户类型筛选。客户类型历史字段可保留兼容，但不在新 UI 中要求填写或管理。

### 5.2 左栏：会话列表

左栏用于快速判断“应该先处理谁”，每条会话展示：

- 平台头像与群名。
- 前两个标签及剩余数量 `+N`。
- 会话状态与服务账号。
- 最近消息摘要、时间和未读数。

左栏标签仅供扫读；点击整行进入会话，不在列表中直接编辑标签。

### 5.3 中栏：消息线程与回复

中栏是主工作区。

会话头部采用紧凑单行结构：

```text
头像 · 群名 · 平台 / 服务账号 / 可回复状态                 标签（最多 5 个）· 编辑图标
```

- 不显示“打开原生会话”。
- 不默认展开消息搜索、日期、附件等低频筛选工具。
- 渠道标签使用描边样式；工作台标签使用浅色实心样式。
- 标签编辑器是点击铅笔图标后出现的浮层，不占据头部高度。
- 消息支持入站、外发、引用、附件、图片和状态。
- 回复框固定于中栏底部，支持多行文本、附件、表情、引用回复、Enter 发送与 Shift + Enter 换行。

### 5.4 右栏：会话处理

右栏不重复展示群名、标签、平台或服务账号，而只提供处理当前会话所需内容：

1. 会话状态。
2. 最近内部备注、备注输入和查看全部。
3. 当前查看/输入坐席与最近操作动态。
4. 可折叠的渠道与发送状态。

当账号离线、账号发送关闭、无回复权限或熔断时，“渠道与发送状态”应自动展开并突出异常原因；回复框同时禁用发送并说明原因。

### 5.5 响应式

| 宽度 | 布局 |
| --- | --- |
| `≥1440px` | 完整三栏：会话列表、消息线程、会话处理。 |
| `1180–1439px` | 压缩服务账号导航与栏宽，消息线程优先。 |
| `<1180px` | 会话处理栏变为右侧抽屉。 |
| 手机端 | 会话列表、消息线程和会话处理以页面/全宽抽屉切换。 |

任意宽度下不得产生横向溢出；长群名、长账号名和长标签均应截断并保留完整内容提示。

## 6. 标签规则

### 6.1 渠道原生标签/分组

- 来源于 WA 标签、TG 文件夹或渠道同步分组。
- 以 `platform + service account + group_id` 隔离。
- 工作台仅同步、展示和筛选，不提供编辑能力。

### 6.2 工作台标签

- 是内部作业标签，可多选。
- 用于横向标记，例如“需报价”“重点”“资料待补”。
- 必须避免与会话状态重复；“待处理/跟进中/已解决”属于状态，不属于标签。
- 仅有 `can_manage` 的坐席可以编辑或新建。
- 标签只保存在工作台自身数据库，不写回 WA/TG。

## 7. 外发与真实发送控制

### 7.1 外发原则

外发采用以下事实源和执行模型：

```text
数据库账本 = 事实源
文件门铃 = 唤醒信号
定时扫描 = 丢失门铃的保险
账号 Worker = 唯一真实发送者
```

浏览器和 API 请求线程都不得直接持有或调用 WA/TG session。

### 7.2 发送双开关

真实发送必须同时满足：

```text
WORKBENCH_SEND_ENABLED = 1（全局开关）
账号 send_enabled = 1（服务账号开关）
坐席具备 can_reply
账号在线且未熔断
```

当前生产环境的全局开关已启用。账号级开关、账号发送限速、失败熔断与 Telegram FloodWait/PeerFlood 暂停机制仍然有效。系统不会因为全局开关开启而主动创建新消息；只有坐席提交回复后才会产生外发任务。

### 7.3 发送状态

外发任务展示并审计以下状态：

```text
pending → sending → sent → delivered（仅 WA 有可靠 ACK 时）
                 ↘ failed → dead
pending/sending → paused / canceled
```

Telegram 不伪造 `delivered`；成功发送后保留 `sent`。

## 8. 数据与系统边界

工作台拥有自己的：

- `auth.sqlite`：用户登录与会话。
- `workbench.sqlite`：外发账本、已读、标签、备注、会话状态与审计。
- `raw.sqlite`：工作台渠道账号采集的消息和群数据。
- `runtime.sqlite`：登录任务、Worker 租约和运行态。

工作台不得读取、写入或依赖监控项目的 SQLite、登录、前端路由、session 或 Worker。工作台不使用监控项目的 AI、告警、画像、知识库或分析数据。

## 9. 非功能需求

### 9.1 安全

- 采用服务端 SSO 回调和 HttpOnly Cookie 会话；前端不保存 SSO Token。
- 写操作进行 CSRF、同源与权限校验。
- 安全响应头包括 CSP、HSTS、X-Frame-Options、Referrer-Policy 和 Permissions-Policy。
- 附件通过鉴权流式接口读取，危险类型强制下载，不暴露本地绝对路径。

### 9.2 可靠性

- 同账号外发严格串行，并应用渠道级最小间隔与每分钟限额。
- 发送失败、FloodWait、PeerFlood、重启恢复和 Worker 容量等待必须可审计、可见。
- `/healthz` 用于进程存活；`/readyz` 用于数据库、Worker、积压和过期任务就绪检查。
- SQLite 每日/每周备份，恢复必须先在临时目录完成完整性校验。

### 9.3 性能与体验

- 首屏优先保障会话列表和消息线程可用。
- 管理、服务账号和登录页异步加载。
- 不因右栏、长文本或标签过多压缩消息阅读区。
- 每个非渠道前端 Chunk 应控制在合理体积内，主入口 gzip 目标小于 250KB。

## 10. 验收标准

### 功能验收

- 坐席只能看到授权服务账号和会话范围。
- 群名行能展示最多 5 个标签；第 6 个起以 `+N` 收纳。
- 渠道标签不可编辑，工作台标签可在会话头部浮层编辑。
- 客户类型不在工作区、筛选或服务账号页展示。
- 会话状态和内部备注能按权限保存并立即反馈。
- 回复只能通过工作台账本创建，重复提交不重复发送。
- 全局或账号级发送开关关闭时，真实发送不会发生。
- 全局和账号级发送开关开启、权限满足且账号健康时，Worker 可以真实发送。

### 界面验收

- 会话头部为紧凑单行，不得被标签编辑表单撑高。
- 标签编辑器必须是独立浮层，拥有清晰边界，不遮挡或挤压消息线程。
- 桌面三栏、1180px 抽屉和手机端布局均无横向溢出。
- 长群名、长账号名、长标签和附件文件名均可读、可截断、可查看完整信息。

### 发布验收

- `npm test`、生产构建、依赖树与生产依赖审计通过。
- 新 Pod 处于 `Running / Ready`，无持续重启。
- API/UI、登录 Worker、账号 Supervisor 都正常启动。
- 未登录访问生产域名跳转统一 SSO。

## 11. 后续迭代原则

后续需求必须优先提升坐席处理效率、发送可靠性或权限安全。任何 AI、监控分析、画像、知识库、自动化营销或复杂工单能力，都不属于当前工作台产品范围，需单独立项和评审。
