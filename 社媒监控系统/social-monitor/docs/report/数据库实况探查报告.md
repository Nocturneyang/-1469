## 八·补充、【新模块方向】短信内容审核知识库 ✏️ 新增

> [!IMPORTANT]
> 用户建议：对同一群组内「提交短信内容审核 → 供应商评价」的对话进行结构化分析，提炼内容共性/差异点，以及供应商对内容的审核要求范式，形成可积累的知识库。

### 业务场景还原

```
 外部联系人（如Pedro, Dexter）          ITNIO运营/技术人员
         │                                      │
         │  「check this content」               │
         │  [粘贴营销SMS文本+链接]  ──────────────▶│
         │                                      │  检查是否被过滤
         │                                      │  (向供应商确认)
         │                                      │
         │◀────────── 「can send / can't send」 ──│
         │            「content 被 filtered」      │
         │            「需要改 xxx 才能过」        │
```

这个对话模式在数据库中大量存在（涉及群：Agil、Chinasky、Gazeti、Chinasky+Telecall等），但目前完全没有被提取和分析。

### 三个层次的分析维度

| 层次 | 分析内容 | 价值 |
|------|---------|------|
| **内容共性** | 提交审核的SMS中，频繁出现哪些词汇/结构？　哪些营销模板被反复使用？ | 了解客户内容偏好 |
| **内容差异** | 同一客户的不同版本内容有什么差别？哪个版本「过了」？ | 提炼有效 vs 无效内容规律 |
| **供应商评价** | 供应商说了什么？可以发/不能发的判断理由？建议改哪里？ | 积累每个供应商的审核标准 |

### 可提取的核心知识

```
1. 【白名单词汇】供应商明确表示可以包含的词/格式
   例：某供应商表示 「加 shortcode 就能过滤器」

2. 【黑名单词汇】导致被过滤/拒绝的词汇
   例：「免费」「立即领取」「100%」等高风险词

3. 【各供应商审核严格度】
   例：Chinasky vs Agil，谁对链接类内容更严格

4. 【内容模板库】历史上成功通过的短信模板
```

### 实现路径（最小可行版）

```javascript
// content-review-extractor.js（建议新建）
// Step 1: 识别内容质检对话
// 触发词：「check this content」「can you send」「check the sms」
//         + 消息长度 > 80字符（说明附带了实际内容）

// Step 2: 提取「内容提交」消息（外部联系人发出）

```

> [!TIP]

### 发现1：真实「零成功率」告警仅8条，而非287条

`0%` 命中287条 → 但 `0% + delivery/route/success` 组合只有 **8条**。
这8条才是真实的成功率告警，287条中其余279条是噪音（价格/数量/日期等数字语境）。

```
关键词精化：
❌ 0%           → 误报279/287（96%误报率）
✅ 0% delivery  → 精准告警（7次）  
✅ send failed  → 精准告警（8次）
✅ not working  → 精准告警（7次）
```

### 发现2：营销短信内容「侵入」群组（两类业务混合）

群组中大量出现的葡语/西语消息**不是供应商在用葡语/西语对话**，而是：
- 供应商把要发给终端用户的**营销短信内容**贴到群里，让对方帮「检查内容是否会被过滤」
- 本质是：`check this content → send test → report delivery result`

这意味着：**「内容质检」是一个高频业务流程**，原方案设计的分析维度里完全没有这个场景。

### 发现3：博彩类SMS流量是正常业务 ✏️

链接分析发现大量 `xxx888.live`、`mt149.online?a=b02` 等博彩类域名。
这些URL出现在供应商和支持人员的对话中，是供应商贴出的**营销短信样本内容**，用于质检测试——**博彩类客户流量是正常业务，无需额外关注**。
分析器设计时可将此类链接归类为「内容质检消息」，区别于技术告警处理。

### 发现4：「主动运维」vs「被动响应」无法区分

`check`（142次）、`test`（59次）、`checking`（34次）是全库最高频的操作词，远超故障词。
这些词既出现在「我去帮你查一下」（主动运维，不需要推送），也出现在「快来查，出问题了」（需要推送）。
**原方案把 `check` 归为中性词是正确的，但需要方向词辅助判断**：
- `pls check` = 请求方说 → 意味着对方发现了问题
- `checking now` / `will check` = 响应方说 → 正在处理，不需要告警

### 发现5：发言人中存在「系统账号」混入

发言人画像中 `ITNIO Support3`（49条，活跃9个群）、`A-Support`（130条，活跃11个群）这类账号**跨多群高频发言**，很可能是：
- 客服机器人或共享客服账号
- 这类账号的发言不应该触发「单人发言异常」告警

```
down, fail, failed, error, issue, offline, blocked, suspended,
```

### 🟡 P2 级（结合频次判断，单条不触发）
```
check（多条在5分钟内 + 同一群 → 可能有问题）

traffic（流量词，看变化趋势）
```

### ❌ 删除（零命中或高误报）
```
崩、断、挂、掉了、异常、故障、中断、不通、跌（全部零命中）
0%（单独使用，96%误报率）
```

## 十、对原推送方案的修订建议（基于事实）

### ✅ 原方案中验证正确的判断
1. **供应商技术告警是核心需求** — 数据100%支持，几乎所有群都是供应商技术群
2. **轮询扫描 + 关键词预筛架构** — 合理，日均170条完全适合
3. **群组沉默检测** — 价值确认，已有12个群静默超过24h

### ❌ 原方案需要修订的内容

**修订1：关键词列表需全面英文化**
```
删除（零命中）: 崩、断、挂、掉了、异常、故障、中断、不通、跌
重点英文词: down, issue, fail, failed, error, offline, undelivered, 
            blocked, suspended, 0% delivery, routing issue, 
            bind is down, please check, pending
```

**修订2：`0%` 不能单独作为告警触发词**
- 实测287条命中，误报率极高
- 必须组合：`0%` + (`delivery`/`rate`/`success`) 才有意义
- 或改为：5分钟内同一群出现3条以上含 `0%` 的消息 → 才触发

**修订3：当前无"客户群"数据，`client-analyzer.js` 暂无数据源**
- 现有46个群均为供应商技术群，命名规律是「编号+供应商名」
- 建议先聚焦 `supplier-analyzer.js`，等客户群接入后再实现客户分析器

**修订4：AI Prompt 需改为多消息聚合输入**
- 平均消息长度62字符，单条毫无可分析意义（如 "bind is down", "pls check"）
- 正确姿势：将5分钟窗口内同一群组的3-15条消息**合并后**送给AI

**修订5：消息高峰在 14:00-19:00 和 20:00-00:00**
- 轮询间隔可在峰值时段从30s降至15s
- 凌晨 06:00-09:00 流量极低，轮询可降频至60s节省资源
