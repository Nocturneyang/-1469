# 知识资产体系设计与实施路线

## 目标

把历史消息和实时消息中的候选资产，沉淀为可复用、可追溯、可审核、可被业务页面调用的正式知识资产。

## 阶段状态

| 阶段 | 目标 | 当前状态 |
|---|---|---|
| 阶段 1：资产发现候选池 | 从消息中抽取 8 类候选资产，支持筛选、评分、证据链、审核 | 已完成 |
| 阶段 2：正式资产沉淀 | 已确认候选转入正式资产库，支持合并、失效、证据追溯 | 实施中 |
| 阶段 3：业务系统集成 | 供应商画像、告警、问题处理页可引用正式资产 | 实施中 |
| 阶段 4：AI 增强与质量闭环 | AI 语义归并、根因总结、人工反馈评估准确率 | 待扩展 |

## 正式资产模型

正式资产统一落入 `knowledge_assets`，不为每个类型单独建表。原因：

- 8 类资产都需要相同的审核、来源、评分、生命周期字段。
- 后续可以按 `asset_type` 拆不同展示，不必先拆物理表。
- 支持一个正式资产关联多个候选资产，避免重复资产扩散。

核心字段：

- `asset_uid`：正式资产唯一 ID。
- `asset_type`：实体关系、联系人角色、运营动作、风险模式等。
- `asset_key`：同类资产的业务去重键。
- `title` / `summary`：展示标题和摘要。
- `status`：active、inactive、merged、deprecated。
- `collection_region` / `business_region` / `business_sector`。
- `group_name` / `receiver_account`。
- `source_candidate_keys` / `source_msg_ids`。
- `evidence` / `metrics` / `related_entities`。
- `confidence` / `asset_value_score` / `quality_score`。
- `usage_count` / `last_used_at`：业务调用后的使用反馈。

候选到正式资产的关系落入 `knowledge_asset_links`。

## 候选资产转正式资产规则

1. 人工点击“确认资产”时：
   - 候选状态变为 `confirmed`。
   - 系统按 `asset_type + asset_key + 区域 + 板块 + 群` 查找正式资产。
   - 找到则合并证据、频次、来源消息、置信度和价值分。
   - 找不到则新建正式资产。

2. 人工点击“标记已合并”时：
   - 候选保留为 `merged`。
   - 后续可指定目标正式资产。

3. 人工点击“废弃”时：
   - 候选不进入正式资产。

## 第一批业务集成

优先接入 3 个最容易产生价值的地方：

1. 供应商画像详情：
   - 展示联系人角色、有效动作、风险模式。
   - 回答“这个群该找谁、常见问题是什么、哪些动作有效”。

2. 资产发现详情：
   - 显示候选是否已经沉淀为正式资产。
   - 支持“确认并沉淀”。

3. 正式资产工作台：
   - 区分候选资产和正式资产。
   - 支持按类型、区域、板块、状态、价值搜索。

## AI 增强边界

AI 不直接写正式资产，只产生建议：

- `ai_summary`：语义摘要。
- `ai_tags`：能力/风险/动作标签。
- `ai_merge_suggestion`：建议合并到哪个正式资产。
- `ai_confidence_reason`：置信度解释。

正式入库仍需规则校验或人工确认。

## 验证标准

- 候选资产确认后，正式资产数量增加或已有资产被合并。
- 来源消息、候选 key、证据链完整保留。
- 供应商画像能展示与该群相关的正式资产。
- 导出和前端展示不暴露密码、手机号、邮箱、URL 原文。
- 专项测试覆盖 schema、API、前端入口、沉淀逻辑和业务引用。
