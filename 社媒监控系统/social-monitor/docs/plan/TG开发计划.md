  ---
  安全设计（最高优先级）

  1. Session String 保护机制

  MTProto 登录后会生成 Session String（等同于账号完整控制权），必须：
  - 存储在 .env 文件中（已在 .gitignore），绝不写入数据库明文
  - UI 界面仅展示脱敏状态（****），不回显原值
  - 支持 Session 撤销：通过 Telegram 设置 → 活跃会话 → 终止指定 session

  2. 登录流程安全设计（手机号 → 验证码 → 2FA）

  登录需要通过服务端完成（不能在前端），流程：                                                                        
  前端输入手机号 → API发起登录 → Telegram推送验证码到手机
  → 前端输入验证码 → 服务端完成认证 → 生成 Session String → 存入 .env                                                 
  → 若启用了2FA密码 → 前端输入密码 → 完成

  3. 风险隔离原则

  - 每个 TG 用户账号独立进程（与现有 worker-tg-{name} 模式一致）
  - Flood Wait 错误（420）自动退避，不崩溃进程
  - Session 文件/字符串禁止同步到代码仓库

  4. 数据获取频控与防封控策略 (风控规避)

  在设计 Telegram 历史数据采集与实时监听时（特别是使用 MTProto API 模拟用户行为时），必须将防封禁（Anti-Ban）机制作为核心考虑因素，确保长期稳定采集：

  - 请求限流与随机抖动 (Rate Limiting & Jitter)：API 请求之间必须增加 2s ~ 5s 的随机休眠时间，模拟真实人类行为。避免 24 小时不间断的无脑轮询，应设计符合当地时区的“休息时间”。
  - 严格响应 FloodWait 异常退避：如果遇到 Telegram 抛出 FloodWaitError，必须在代码层面捕获该错误，并严格按照其要求的秒数进行休眠后才可重试，切勿强行绕过。
  - 分批获取与断点游标 (Batch & Cursor Control)：历史消息追溯时，单次请求的数据量应限制在 50-100 条以内。引入游标持久化机制，即便进程被中断，重启后依然可以断点续传。
  - 账号权重与养号机制：新注册账号极易触发风控。对于新号，应在初始阶段设置极低的日均请求上限（例如每日仅拉取几百条），随着账号存活时间的增加，再逐步放开限制。
  - 熔断预案：设置进程级熔断：若账号进入受限状态（如被系统标记为 PeerFlood 只能双向联系人私聊），必须自动中止该账号的采集任务，并向管理员推送钉钉告警。

  4. 新建 lib/tg-backfill-queue.js — 历史消息回溯队列
    - 持久化队列：db/analytics.sqlite 新增 tg_backfill_tasks 表，记录每个群的回溯进度（chat_id, offset_id, status, daily_count, created_at）
    - 断点续传：进程重启后从 offset_id 继续，不重头拉取
    - 串行单线程：同一时刻只处理队列中一个群的一批次任务

  关键代码结构：
  worker-tg-user.js
    └── 初始化 TelegramClient (gramjs)
    └── 若无 Session → 触发登录流程（通过 server.js API 交互）
    └── 登录成功 → 进入 [预热期 warmup_seconds，默认600秒]
         └── 预热期内：仅监听 NewMessage 实时事件，不主动拉取历史
         └── 预热期结束后：启动后台回溯队列（tg-backfill-queue.js）
    └── 回溯队列（后台低优先级线程）：
         └── 从 tg_backfill_tasks 取队首任务
         └── 调用 GetHistory(chat_id, offset_id, limit=100)
         └── 写入 database.sqlite
         └── 更新 offset_id 和 daily_count 游标
         └── 强制 Sleep(random 3s~8s) 再取下一批
         └── 达到日拉取配额（daily_limit）→ 暂停到次日 00:00 再续
    └── FloodWaitError → 严格按返回的秒数休眠，不崩溃进程
    └── PeerFloodError → 触发进程级熔断，推送钉钉告警，暂停24小时

  Phase 2 — 服务端登录 API + 频控配置 API（UI 交互核心）

  在 server.js 新增以下 TG 用户账号相关 API：

  [登录流程]
  POST /api/tg-user/start-login          — 发起登录，输入手机号，返回 phoneCodeHash
  POST /api/tg-user/verify-code          — 输入验证码，完成或触发2FA
  POST /api/tg-user/verify-2fa           — 输入2FA密码，最终完成登录，保存Session
  GET  /api/tg-user/status/:name         — 查询账号状态（session是否有效）
  POST /api/tg-user/revoke/:name         — 撤销Session，停止进程

  [频控配置（新增）]
  GET  /api/tg-user/ratelimit/:name      — 读取当前账号的频控配置
  POST /api/tg-user/ratelimit/:name      — 更新频控配置，写入 .env
    参数：{
      warmup_seconds: 600,       // 登录后预热静默期（秒，默认600=10分钟）
      daily_limit: 2000,         // 每日历史消息最大拉取条数
      batch_size: 100,           // 每批次拉取条数（50~200）
      sleep_min_ms: 3000,        // 批次间最小间隔（毫秒）
      sleep_max_ms: 8000,        // 批次间最大间隔（毫秒）
      backfill_days: 7,          // 历史回溯天数（0=不回溯，-1=全部）
      enable_backfill: true      // 是否开启历史回溯
    }

  [回溯任务管理（新增）]
  GET  /api/tg-user/backfill/:name       — 查看回溯任务列表及进度
  POST /api/tg-user/backfill/:name/pause — 暂停回溯（不影响实时监听）
  POST /api/tg-user/backfill/:name/reset — 重置某群回溯进度（重头开始）

  登录状态机：
  idle → logging_in（等验证码）→ need_2fa（等密码）→ warmup（预热期）→ monitoring（实时监听+后台回溯）→ disconnected
  - 登录过程中的临时状态（phoneCodeHash、client实例）存服务端内存，有效期5分钟超时清理
  - warmup 状态持续 warmup_seconds 后自动转为 monitoring 并启动回溯队列
