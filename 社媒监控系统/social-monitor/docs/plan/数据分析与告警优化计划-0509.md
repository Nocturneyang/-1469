## 二、分业务板块内容深度分析

### 2.1 设备供应商（17,185 条 | 197 群 | 我方=SKYLINE团队）

#### 内容特征
- **高频词：** port/端口(726)、SIM/卡(764)、restart/重启(203)、IMEI(130)、goip(高频)、modem、gateway
- **核心场景：**
  1. **设备配置与初始化** — 「帮我配置这个设备」「能不能开一下端口」
  2. **故障排查** — 「为什么不工作」「一直断链」「重启一下」
  3. **远程协助** — Anydesk/TeamViewer 远程排障（最高频协作模式）
  4. **端口/IP续费** — 「100 ports renew」「another cloud sever」
  5. **SIM/IMEI 管理** — IMEI 变更、SIM 卡替换、插卡检测

#### 现有告警覆盖评估
| 告警场景 | 现有覆盖 | 缺口 |
|---|---|---|
| 设备离线/断连 | P1关键词「down」「offline」 | 设备特有的「can't connect」「disconnect」「not responding」未独立建模 |
| 端口/IP故障 | 无专门规则 | **缺少设备端口层告警**，端口过期/耗尽场景未监控 |
| SIM卡问题 | 无专门规则 | SIM 失效、IMEI 不匹配是高频问题 |
| 远程无法连接 | 无专门规则 | 「anydesk not working」场景频繁 |

#### 人物角色分类
| 角色 | 代表发言人 | 消息占比 |
|---|---|---|
| SKYLINE技术支持（我方） | SKYLINE TECH SUPPORT, SKYLINE Technical Support 等 | 36% |
| 外部设备买家/客户 | Vince Gill, 1% (GW), VA, Robert Chi 等 | 58% |
| 设备供应商商务 | Petrichor, 金铃铛, Chinaskyline | 6% |

**我方发言人识别准确度：** 基于 `staff-detector.js` 的关键词 `SKYLINE` 能覆盖 5,363/5,396 条（99.4%），匹配度很高。

### 2.2 直连供应商（6,013 条 | ~78 群 | 我方=ITNIO/Routing/Jasmine）

#### 内容特征
- **高频词：** SID(350)、DLR/送达(142)、route down(200)、blocked/spam(112)、rate/price(129)
- **核心场景：**
  1. **通道质量监控** — 「DLR delay」「click ratio too low」「route quality degradation」
  2. **SID管理** — 每日大量 SID 提供/更新/测试（单条消息可达20+ SID）
  3. **内容审核/拦截** — 「content is blocked by smsfw」「spam」「content flagged」
  4. **价格/费率谈判** — 「rate is 0.0019usd」「price adjustment」
  5. **通道故障响应** — 「route is completely down」「service not working」

#### 现有告警覆盖评估
| 告警场景 | 现有覆盖 | 缺口 |
|---|---|---|
| 通道完全故障 | P0 正则 + P1 关键词 | ✅ 覆盖较好 |
| DLR/送达率异常 | P1「undelivered」 | ❌ **缺少数值化阈值**（如 DLR<50% 持续10分钟） |
| SID批量变更 | SID检测已有 | ✅ 覆盖较好 |
| 内容被拦截 | P1「blocked」 | ❌ 缺少「smsfw」「spam filter」等特定词 |
| 点击率下降 | **无规则** | ❌ 重要缺失 — click ratio 是核心KPI |
| 垃圾流量干扰 | **无规则** | ❌ 「spam traffic from another supplier」场景 |

### 2.4 客服（1,672 条 | 13 群 | 我方=客服-Momo）

#### 内容特征
- **高频词：** OTP(284)、not receive(231)、channel(79)、template(25)
- **核心场景：**
  1. **OTP 未送达排查** — 「Player didn't receive the OTP code」（最高频）
  2. **短信模板审核** — 赌博/游戏类营销短信内容审核
  3. **短链接测试** — 「content test」「link check」
  4. **号码送达确认** — 「这两个号码的送达情况」
  5. **通道选择建议** — 「直连就跟你那个发你自己主体一样 测下就好」

#### 现有告警覆盖评估
客服场景**基本完全游离在现有告警体系之外**。当前 supplier-analyzer 的 P0/P1 规则针对供应商通道故障设计，对客服 OTP 场景无效。

**需要独立告警体系：**
- OTP 送达率异常（单号码/批量）
- 模板被运营商拦截
- 短链接被封禁

#### 客服 QA 知识积累潜力（极高价值）
客服群聊是**最规范的结构化对话**，天然适合构建 FAQ 知识库：
- 客户提问 → 客服-Momo 解答的模式非常稳定
- 问题类型高度集中（OTP送达、模板审核、通道选择）
- **Momo 是唯一我方发言人在此板块**，对话模式极其清晰

## 五、脱离告警的数据资产探索

### 5.1 供应商画像系统（高价值 ★★★★★）

基于群聊数据，为每个供应商建立动态画像：

| 维度 | 数据来源 | 价值 |
|---|---|---|
| **响应速度** | 问题提出→供应商首次回复时间差 | 供应商SLA量化 |
| **问题复发率** | 同群同类问题重复次数（已有 recurrence_count） | 供应商稳定性评估 |
| **承诺兑现率** | commitment_due vs 实际闭环时间 | 供应商可信度 |
| **单次故障时长** | issue 打开到关闭的 duration_mins | 故障恢复能力 |
| **沟通语言/时区** | sender 消息时间分布+语言检测 | 运营排班参考 |

### 5.2 设备故障知识图谱（中价值 ★★★★）

从设备供应商对话提取：
- **设备型号 → 常见故障 → 解决方案** 的知识关联
- 例如：「RFH0606938SM → 模块4-8不工作 → 拆卸重装」
- 可用于：新客户自助排查、SKYLINE 新人培训

### 5.3 内容模板库（中价值 ★★★★）

从客服群提取：
- 各客户（Onbuka/JILI/LAAFFIC等）的短信模板库
- 不同地区/运营商的合规要求积累
- 模板 A/B 测试效果数据

### 5.4 供应商关系图谱（低价值 ★★★）

- 哪些供应商有关联关系（同群出现）
- 供应商→客户的路由关系
- 可用于：通道故障时的替代方案推荐

## 六、群聊价值标签体系（L0~L3）

### 6.1 设计初衷

不同群聊的业务重要性差异巨大——部分群聊是核心通道供应商的日常运维群，必须实时监控；部分群聊仅供设备类偶尔支持使用，告警优先级较低。需要通过价值标签实现**差异化的告警策略和推送策略**。

**标签由运营人员手动配置，系统只读取标签并据此调整行为，不做自动判定。**

### 6.2 标签定义

| 标签 | 含义 | 手动配置参考 | 告警行为 | 推送行为 |
|---|---|---|---|---|
| **L0** | 关键通道/高价值群 | 核心直连供应商群、主要语音通道群、历史曾触发 P0 的高活跃群 | 全量告警（P0/P1/P2）+ 无响应检测 + SID变更 | 日报重点呈现 + 周报评分 |
| **L1** | 常规供应商/活跃群 | 一般直连/语音供应商群、活跃设备售前群（**缺省值，新账号默认 L1**） | P0/P1 告警 + 无响应检测 | 日报纳入 + 周报评分 |
| **L2** | 低优先级/偶发群 | 低频设备售后群、历史无 P0 告警的低活跃群 | 仅 P0 告警 | 日报沉默提醒 + 不纳入周报评分 |
| **L3** | 观察/归档群 | 测试群、已停用供应商群、不再维护的历史群 | 完全静默 | 不推送，仅存档 |

### 6.3 配置方式

**全部由运营人员手动维护**，系统不做自动标签赋值。

在 `account-regions.json` 中为每个 account 新增 `value_label` 字段（可选，缺省为 L1）：

```json
{
  "accounts": [
    {
      "account": "wa-oumei_wa",
      "region": "欧美区",
      "platform": "wa",
      "value_label": "L0",
      "owner": "Jasmine-001",
      "description": "欧美区主力账号，核心直连通道群"
    },
    {
      "account": "wa-wa_shebi",
      "region": "WA设备技术",
      "platform": "wa",
      "value_label": "L2",
      "owner": "",
      "description": "设备技术服务，非核心通道"
    }
  ]
}
```

## 七、现有告警体系问题诊断

### 7.1 当前告警架构

```
supplier-analyzer.js（统一引擎）
  ├── P0: 10条正则 → 直接推送
  ├── P1: 18个关键词 → 5分钟窗口聚合 → AI评分≥7推送
  ├── P2: 15分钟无响应 → 推送
  └── SID: ≥3个SID → 推送

issue-lifecycle-tracker.js
  ├── 30分钟未闭环 → 提醒
  ├── 2小时未闭环 → 升级
  └── 承诺到期 → 未兑现告警
```

### 7.2 核心问题

#### 问题1：告警规则「一刀切」，未区分业务板块
所有业务板块共用同一套 P0/P1 规则，导致：
- `port` 在设备供应商是中性词（端口配置），不会被告警
- 但语音线路的 `503` 是严重错误，却在当前规则中完全不被识别
- 客服的 OTP 送达问题完全被忽略

**实际告警分布：** P0=67条, P1=296条（4月至今），说明告警频率已经相当高

#### 问题2：缺少数值化质量阈值
当前告警仅依赖关键词匹配，无法识别：
- DLR 从 95% 降到 60%（关键词不会触发但业务影响严重）
- ASR 持续下降趋势
- 单群消息量突然暴涨（可能是故障爆发）

#### 问题3：internal-staff.json 白名单严重不足
- 精确匹配仅 3 条
- 大量我方人员依赖关键词误打误撞
- `Support` 关键词会误匹配外部供应商的 Support

#### 问题4：客服板块完全无告警覆盖
1,470 条客服消息中 OTP 未送达是最核心场景，但告警体系完全未涉及。

#### 问题5：缺少「恢复确认」机制
闭环检测依赖后续消息中的「resolved/fixed/back to normal」等词，但在设备供应商场景中，问题解决往往是「好了」「可以了」「working now」等简短确认，当前正则可能遗漏。

## 十、关键技术问题与解决方案

### 问题一：日报区域定向推送 — 确保内容不跨区泄漏

#### 现状分析

当前 `daily-digest.js` 推送逻辑：
1. 查询昨日活跃群（`msg_count >= 5`），按 `receiver_account` 排序
2. 通过 `getRegionLabel(receiver_account)` 从 `account-regions.json` 获取 `region`
3. 按 `platform` 分组，检查 `hasRegionalWebhook('DIGEST', platform, region)` 
4. 有专属 Webhook 的区域独立推送，其余合并为"全局日报"

#### 存在的问题

| 问题 | 影响 |
|---|---|
| **仅按 region 路由，未考虑 business_sector** | `DIGEST_wa_WA设备技术` 和 `DIGEST_tgu_TG-设备支持` 在 webhooks.json 中以 sector 命名，但代码只匹配 region，实际这些 account 的 region 字段恰好等于 sector 名，属于"巧合正确" |
| **全局兜底推送可能包含不应推送的内容** | 无专属 Webhook 的区域/板块内容全合并推送，接收方可能看到无关内容 |
| **region 字段语义不统一** | `account-regions.json` 中有的 region 是地理区域（欧美区），有的是业务板块（WA设备技术），有的是混合（TG-设备支持） |

#### 解决方案：双维度路由（region + business_sector）

**核心思路：** 日报推送的 Webhook 匹配 key 改为 `${TYPE}_${platform}_${region}_${business_sector}`，按优先级逐级 fallback。

```
Webhook 匹配优先级（从高到低）：
  1. DIGEST_wa_欧美区_直连供应商     → 最精确
  2. DIGEST_wa_欧美区                → 区域兜底
  3. DIGEST_wa                       → 平台兜底
  4. DIGEST                          → 全局兜底（ENV）
```

**代码改动点（daily-digest.js：processGroup 函数和推送循环）：**

    if (!digestText) continue;
    if (group.webhook) {
      await _send(group.webhook.url, group.webhook.secret, buildMarkdown(title, digestText));
    } else {
      await dingtalk.sendDigest({ title, content: digestText, platform }); // 全局兜底
    }
  }
}

### 问题二：P0/P1 告警必须基于上下文判断

#### 现状分析

当前 P0/P1 告警的致命缺陷：**只看单条消息的文本，不看对话上下文**。

典型误报场景：
```
外部：Is the route still down?           → 触发 P0 "route down" 正则
内部：Yes it was down yesterday but fixed → 这是确认已恢复，不是新故障！
```

典型漏报场景：
```
外部：Having some issues with delivery    → "issues" 触发 P1 关键词
外部：All messages are returning 0% success → 没有 P0 正则命中（"0% success" 被后面的文字稀释）
```

**核心问题：当前 P0 是纯正则单条消息匹配，没有任何上下文。**

#### 解决方案：上下文窗口 + AI 二次确认

**方案设计（不改变现有架构骨架，增量改造）：**

```
┌──────────────────────────────────────────────────────────────┐
│                    P0/P1 上下文告警流程                        │
├──────────────────────────────────────────────────────────────┤
│  1. 关键词/正则命中（初筛，和现在一样）                          │
│     ├── P0 正则命中 → 进入 P0 上下文验证                       │
│     └── P1 关键词命中 → 进入 P1 窗口聚合（不变）                 │
│                                                                  │
│  2. P0 上下文验证（新增）                                       │
│     ├── 查询同群前 15 条消息（按 timestamp ASC）                │
│     ├── 构建对话窗口：                                          │
│     │   [前15条] + [触发消息] + [后3条如果有]                    │
│     ├── 调用 AI（轻量 Prompt，~200 tokens）判断：                │
│     │   {                                                      │
│     │     "is_genuine_alert": true/false,                      │
│     │     "reason": "新故障报告" / "历史问题讨论" / "已恢复确认", │
│     │     "severity": "p0" / "p1" / "false_alarm",            │
│     │     "affected_scope": "全群" / "单客户" / "未知"         │
│     │   }                                                      │
│     ├── is_genuine_alert=false → 丢弃（记录 suppressed_alert）  │
│     └── is_genuine_alert=true  → 正常推送                      │
│                                                                  │
│  3. P1 窗口 AI 分析增强（改造现有 analyzeAlertMessages）          │
│     ├── 窗口内消息去重 → 取前 20 条                             │
│     ├── 额外注入：窗口前 5 条消息（上下文锚点）                   │
│     ├── Prompt 增加字段：                                       │
│     │   "is_new_issue": 是否新问题(非历史延续)                   │
│     │   "related_issue_id": 关联的已有 issue ID 或 null         │
│     │   "escalation_needed": 是否需要升级                       │
│     └── AI 返回 false_alarm → 不推送                            │
└──────────────────────────────────────────────────────────────┘
```

  SELECT id, sender_name, content, timestamp
  FROM messages
  WHERE (group_id = ? OR group_name = ?)
    AND id < ?
    AND content IS NOT NULL AND content != ''
  ORDER BY id DESC
  LIMIT 15
`);

// 新增：P0 上下文验证
async function validateP0WithContext(msg, keyword) {
  const contextMsgs = getContextWindow.all(
    msg.group_id || '', msg.group_name, msg.id
  ).reverse(); // 时间正序
  
  if (contextMsgs.length === 0) {
    // 无上下文 → 直接当作真告警（保守策略）
    return { is_genuine_alert: true, reason: '无上下文，默认放行', severity: 'p0' };
  }

  const prompt = buildP0ContextPrompt(msg, keyword, contextMsgs);
  try {
    const text = await callAI(prompt);
    const result = extractJSON(text);
    return result || { is_genuine_alert: true, reason: 'AI解析失败，默认放行', severity: 'p0' };
  } catch (err) {
    if (err.message === 'AI_DEGRADED') {
      // AI 降级 → 回退到纯关键词模式（和旧行为一致）
      return { is_genuine_alert: true, reason: 'AI降级，关键词放行', severity: 'p0' };
    }
    return { is_genuine_alert: true, reason: 'AI异常，默认放行', severity: 'p0' };
  }
}

function buildP0ContextPrompt(msg, keyword, contextMsgs) {

    return `[${t}] ${m.sender_name}: ${m.content}`;
  }).join('\n');

  return `你是ITNIO告警风控引擎的上下文分析器。

触发关键词："${keyword}"
触发消息：[${msg.sender_name}]: ${msg.content}

---

1. 这是新发生的故障报告，还是对历史问题的讨论/确认？
2. 如果是新故障，严重程度是 p0（全群/全通道故障）还是 p1（局部/单客户）？
3. 如果是对历史问题的讨论，是否表明问题已经恢复？

严格JSON输出：
{"is_genuine_alert":true/false,"reason":"一句话原因","severity":"p0"/"p1"/"false_alarm","affected_scope":"全群"/"单客户"/"未知"}`;
}

//   const keyword = matchP0(msg.content);
//   if (!keyword) continue;

//   const keyword = matchP0(msg.content);

**成本优化：上下文缓存**

为避免每条 P0 候选消息都查数据库+调 AI，增加内存缓存：

```javascript
// 同一群 2 分钟内不重复调用 AI 做上下文验证
const p0ValidationCache = new Map(); // key: groupId, value: { ts, result }
const P0_CACHE_TTL = 2 * 60 * 1000;

async function validateP0WithContextCached(msg, keyword) {
  const cacheKey = msg.group_id || msg.group_name;
  const cached = p0ValidationCache.get(cacheKey);
  if (cached && (Date.now() - cached.ts < P0_CACHE_TTL)) {
    return cached.result; // 同一群短时间内的后续 P0 命中复用上次结果
  }
  const result = await validateP0WithContext(msg, keyword);
  p0ValidationCache.set(cacheKey, { ts: Date.now(), result });
  return result;
}
```

## 十二、风险与注意事项

1. **数据时效性**：当前数据集中在 2026年4月-5月，早期的1-3月数据极少，趋势分析需注意样本偏差
2. **business_sector 字段依赖**：当前告警规则中使用 `regionInfo.business_sector` 获取板块，实际数据中该字段已填充，但需确认新增账号时是否正确赋值
3. **TG 平台特殊性**：Telegram 群聊结构和 WhatsApp 差异大（允许编辑/删除消息、支持主题等），告警逻辑需要平台感知
4. **AI 调用成本**：P1 聚合使用 AI 评分，按板块拆分后可能增加 AI 调用量。建议设备供应商板块降低 AI 调用频率（问题更偏技术排查，关键词更可靠）
5. **告警疲劳**：当前 P0=67 + P1=296 在 ~2 个月内，日均 ~6 条告警。规则细化后可能短期增加，需设置告警去重和收敛机制
6. **凭据安全**：`ecosystem.config.js` 当前含硬编码的 TG API 凭据且已提交 git。即使 `.env` 迁移后，git 历史中仍残留旧值，建议轮换所有已泄露的 `TG_API_ID`/`TG_API_HASH`
7. **WAL 模式数据库关闭**：`better-sqlite3` 在 WAL 模式下异常退出可能导致 WAL 文件累积（checkpoint 未执行）。优雅关闭机制必须在所有进程中实施，否则长期运行后磁盘占用增大且启动变慢
