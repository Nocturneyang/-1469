## 一、核心定位升级：从「告警仪表盘」到「供应商协同情报中心」

### 1.1 这些群的本质

监控的群**不是系统日志，而是供应商与 ITNIO 运营之间的协同工作界面**：

```
[供应商技术/运营人员]  ←── WhatsApp 群 ──→  [ITNIO 运营人员]
   持有通道实况                                 需要通道信息
  （最接近基础设施）                           （才能做业务决策）
```

所有关于通道健康状态的信息，以口语化方式流经这里。**供应商是传感器，群聊是数据总线。**

### 1.2 版本2遗漏的核心问题

| 遗漏维度 | 具体问题 |
|---------|---------|
| 只捕捉问题出现 | 没有追踪问题是否被关闭，持续了多久 |
| 忽略对话结构 | 消息不是孤立日志，有来有往，承诺和响应是核心信号 |
| 日报只看「发生了什么」 | 没有「还有什么悬而未决」 |
| 告警广播给所有人 | 没有按区域/负责人分发，责任不清 |
| 无供应商可靠性积累 | 哪个通道最不稳定、哪个供应商响应最慢，完全无数据 |

### 1.3 事实基线（取代假设）

| 原假设 | 实际情况 | 影响 |
|--------|---------|------|
| 中英双语业务环境 | **纯英语**（中文词命中率0%）| 关键词列表需全面英文化 |
| 均匀的供应商/客户群 | **全部是供应商沟通群**，无客户群 | `client-analyzer` 暂无数据源 |
| `0%` 是有效告警词 | 287条命中，**96%是误报** | 必须改为组合词 |
| 单条消息可分析 | 平均**62字符**，碎片化 | AI必须多消息聚合输入 |

## 三、维度1：实时告警推送（分钟级）

### 3.1 关键词规则库（基于实测数据）

#### 🔴 P0 级 — 立即推送（组合词，误报率极低）

```
send failed       0% delivery      not working
bind is down      route down        service down
completely down   failed to deliver
```

#### 🟠 P1 级 — 5分钟内聚合推送

```
down    fail    failed    error    issue
offline blocked suspended rejected undelivered
timeout disconnected pending
```

> [!WARNING]
> `0%` 单独不触发（96%误报率）。必须是 `0% delivery` / `0% success` 等组合才触发。  
> `check` / `test` 单独不触发（主动运维词，不代表故障）。

#### 🟡 P2 级 — 频次触发（单条不触发）

```
规则：5分钟内同一群3条以上含 check/issue → 可能存在持续问题
规则：外部人员连续提问无 ITNIO 响应 → 超15分钟 → 触发「无响应告警」
规则：Samu 等高重复账号内容突变（偏离历史模板>50%）→ 触发P1
```

## 四、维度2：问题生命周期追踪（新增）

> [!IMPORTANT]
> 这是本次方案更新最重要的新模块。实时告警只是「发现问题」，问题是否被处理、被关闭、耗时多久，当前方案完全没有答案。

### 4.1 核心逻辑：告警有开启就必须有关闭

```
告警触发（P0/P1）
    │
    ▼ 写入 issue_records（status = 'open'）
    │
    ├─ 扫描同群后续消息，匹配闭环词：
    │   resolved / fixed / back to normal / working now / all good / done
    │
    ├─ 匹配到 → 标记 status = 'closed'，记录 duration_mins
    │
    └─ 未匹配 → 超时告警
            30分钟后仍 open → 推送「问题未解决提醒」
            2小时后仍 open → 升级推送，@技术人员介入
```

### 4.2 承诺追踪（Commitment Tracking）

供应商在群里的承诺句式，是最高价值的时效性信号：

```javascript
const COMMITMENT_PATTERNS = [
  /will\s+(fix|update|route|check|resolve|get\s+back)\s*(in|by|within|shortly)?/i,
  /(give|update)\s+(you|us)\s+(in\s+)?\d+\s*(min|hour|hr)/i,
  /by\s+(eod|end\s+of\s+day|tonight)/i,
  /checking\s+now[,.]?\s+will\s+update/i,
];

function extractCommitment(msg) {
  for (const pattern of COMMITMENT_PATTERNS) {
    if (pattern.test(msg.content)) {
      return {
        groupName: msg.group_name,
        sender: msg.sender_name,
        commitmentText: msg.content,
        detectedAt: msg.timestamp,
        deadlineGuess: parseDeadline(msg.content),  // 从"in 30 mins"解析截止时间
      };
    }
  }
  return null;
}

// 到承诺截止时间后：检查同群是否出现闭环词
// 无闭环 → 推送「供应商承诺未兑现」提醒给区域负责人
```

### 5.2 `daily-digest.js` 实现逻辑

```javascript
async function generateDailyDigest() {
  const yesterday = getYesterdayRange();

  // ✅ 区域标注从配置文件读取，新增账号只需更新 config/account-regions.json
  const accountConfig = JSON.parse(
    fs.readFileSync('./config/account-regions.json', 'utf8')
  );
  const REGION_MAP = Object.fromEntries(
    accountConfig.accounts.map(a => [a.account, { region: a.region, owner: a.owner }])
  );

  // Step 1: 查询昨日活跃群（含 receiver_account → 区域）
  const activeGroups = db.prepare(`
    SELECT group_name, receiver_account,
           COUNT(*) AS msg_count,
           GROUP_CONCAT(content, '\n---\n') AS content_blob
    FROM messages
    WHERE timestamp BETWEEN ? AND ?
      AND content IS NOT NULL AND receiver_account != 'default'
    GROUP BY group_id
    HAVING msg_count >= 5
    ORDER BY receiver_account, msg_count DESC
  `).all(yesterday.start, yesterday.end);

  activeGroups.forEach(g => {
    g.region = REGION_MAP[g.receiver_account] || '未知区';
    g.displayName = `${g.region}-${g.group_name}`;
  });

  // Step 2: 查询昨日未闭环的 issue_records
  const openIssues = db.prepare(`
    SELECT group_name, issue_type, opened_at, commitment_text
    FROM issue_records
    WHERE status = 'open'
      AND opened_at BETWEEN ? AND ?
    ORDER BY opened_at ASC
  `).all(yesterday.start, yesterday.end);

  // Step 3: 查询沉默群组
  const silentGroups = db.prepare(`
    SELECT group_name, receiver_account,
           ROUND((strftime('%s','now') * 1000 - MAX(timestamp)) / 3600000.0, 1) AS silent_hours
    FROM messages
    GROUP BY group_id
    HAVING MAX(timestamp) < ? AND COUNT(*) > 10
    ORDER BY silent_hours DESC
  `).all(yesterday.start);

  silentGroups.forEach(g => {
    g.region = REGION_MAP[g.receiver_account] || '未知区';
  });

  // Step 4: AI 生成摘要（含未闭环事项注入）
  const summaries = [];
  for (const group of activeGroups) {
    const groupOpenIssues = openIssues.filter(i => i.group_name === group.group_name);
    const filteredContent = filterInternalSenderContent(group.content_blob);

    const aiSummary = await callAI({
      prompt: buildDailyDigestPrompt(group.displayName, filteredContent, groupOpenIssues),
      maxTokens: 250
    });

    summaries.push({
      displayName: group.displayName,
      msgCount: group.msg_count,
      keyPoints: aiSummary.keyPoints,
      followUp: aiSummary.followUp,
      openIssues: groupOpenIssues,          // ← 未闭环事项直接注入
      hasAlert: aiSummary.hasAlert
    });
  }

  const digestText = formatDigest(summaries, silentGroups);
  await sendDingTalkMarkdown({
    title: `📋 供应商群 ${formatDate(yesterday.start)} 日报`,
    content: digestText
  });
}
```

### 6.3 `supplier-reliability-scorer.js` 核心查询

```javascript
// 每周一运行
async function generateWeeklyReliabilityReport() {
  const weekRange = getLastWeekRange();

  const stats = db.prepare(`
    SELECT
      ir.group_name,
      ir.region,
      COUNT(*) AS total_issues,
      AVG(ir.duration_mins) AS avg_recovery_mins,
      SUM(CASE WHEN ir.commitment_met = 1 THEN 1 ELSE 0 END) * 1.0 /
        NULLIF(SUM(CASE WHEN ir.commitment_met IS NOT NULL THEN 1 ELSE 0 END), 0)
        AS commitment_rate,
      COUNT(CASE WHEN ir.status = 'open' THEN 1 END) AS still_open
    FROM issue_records ir
    WHERE ir.opened_at BETWEEN ? AND ?
    GROUP BY ir.group_name
    ORDER BY total_issues DESC
  `).all(weekRange.start, weekRange.end);

  // 计算综合评分（100分制，问题越少分越高）
  const scored = stats.map(s => ({
    ...s,
    score: calcReliabilityScore(s)
  })).sort((a, b) => b.score - a.score);

  await sendWeeklyReport(scored);
}
```

## 八、数据库架构方案

### 8.1 双库分离架构

> [!IMPORTANT]
> 采集库与分析库**完全分离**：采集层对 `database.sqlite` 只写，分析层对其只读，所有分析输出写入独立的 `analytics.sqlite`。两库互不干扰，可独立升级、备份、清理。

```
db/
├── database.sqlite      ← 原始采集库（只读，采集层写入，分析层只读）
└── analytics.sqlite     ← 分析输出库（新建，所有分析模块写入此处）
```

**关键原则**：
- `database.sqlite` — 不做任何 `ALTER TABLE`，保持原始结构不变
- `analytics.sqlite` — 所有分析结果、告警记录、日报、评分均存入此库
- 分析器通过 `analysis_cursor` 表（在 `analytics.sqlite` 中）记录已处理到的消息位置，替代给 `messages` 表加 `is_analyzed` 字段

### 8.2 分析器连接方式

```javascript
const Database = require('better-sqlite3');

// 采集库：只读打开
const sourceDb = new Database('./db/database.sqlite', { readonly: true });
sourceDb.pragma('journal_mode = WAL');

// 分析库：读写，独立文件
const analyticsDb = new Database('./db/analytics.sqlite');
analyticsDb.pragma('journal_mode = WAL');

// 分析器从采集库读取消息，向分析库写入结果
const newMsgs = sourceDb.prepare(`
  SELECT id, sender_name, content, group_name, group_id,
         receiver_account, timestamp, has_media
  FROM messages
  WHERE timestamp > ?
  ORDER BY timestamp ASC
  LIMIT 500
`).all(getLastProcessedTimestamp(analyticsDb));  // 游标从 analyticsDb 读取
```

## 十二、关键技术注意事项

> [!IMPORTANT]
> **防重复分析**：所有分析器通过 `is_analyzed=1` 标记已处理消息，严禁对同一消息重复 AI 调用。

> [!IMPORTANT]

> **AI调用熔断**：出现429/402时切换纯关键词降级模式，同步推送「AI降级通知」。每群每次最多聚合20条消息。

> [!TIP]

> - 14:00-19:00（主峰值158条/h）→ **15秒**
> - 20:00-00:00（夜间活跃110条/h）→ **30秒**
